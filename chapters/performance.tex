\section{処理時間の基準測定}

高速化\index{こうそくか@高速化|textbf}を始める前に、処理時間の内訳を測定する必要がある。データの読み込み、探索、図の作成のどこに時間を要しているかを区別しなければ、変更による効果を適切に評価できない。

\code{time.perf\_counter}\index{perf_counter@\code{time.perf\_counter}|textbf} を使うと、処理の前後で取得した時刻の差から経過時間を求められる。解析全体の所要時間に加えて、データの読み込み、前処理、探索、書き出し、作図という段階ごとの時間も記録すると、変更すべき箇所を特定しやすい。

\begin{lstlisting}[language=Python]
import time

t0 = time.perf_counter()
run_analysis()
t1 = time.perf_counter()
print(f"elapsed = {t1 - t0:.3f} s")
\end{lstlisting}

キャッシュ、OS のスケジューリング、同時に動作するプロセスによって測定値は変動する。入力と実行条件をそろえて複数回測定し、中央値や最小値など、あらかじめ定めた代表値を比較する。

上の \code{run\_analysis()} は、測定対象として読者が定義する解析関数を表す。Python の組込み関数ではない。

\subsection{Jupyter の \code{\%timeit} による計測}

Jupyter の \code{\%timeit}\index{timeit@\code{\%timeit}|textbf} と \code{\%\%timeit} は、短い式またはセルを複数回実行し、所要時間の統計量を表示する。短い処理の比較に用いる。次の例では、別のセルで \code{import numpy as np} と \code{array = np.arange(1000000)} を実行してから、計測セルを実行する。

\begin{lstlisting}[language=Python]
%%timeit
result = array * 2
\end{lstlisting}

ただし、\code{\%timeit} はノートブックや IPython で短い処理を測定する機能であり、スクリプト全体の読み込みや入出力を含めた時間の測定には適さない。短い式や関数には \code{\%timeit}、解析全体には \code{perf\_counter} を使う。

\section{計算量の見積もり}
\index{けいさんりょう@計算量|textbf}
\index{あるごりずむ@アルゴリズム|textbf}

処理時間の測定に加えて、入力サイズに対する演算回数の増加率を見積もる。入力サイズを $N$ としたとき、演算回数が $N$、$N \log N$、$N^2$ のいずれに比例するかによって、大規模入力で必要となる処理量が異なる。

厳密な漸近解析が困難な場合でも、入力サイズを 2 倍にしたときの演算回数を見積もれば、実測値の増加がアルゴリズムから予想される範囲かを検証できる。個々の実装技法を選ぶ前に、問題が必要とする比較・探索・集計の回数を調べる。

変数名を短くしたり、関数を減らしたりしても、通常は実行時間にほとんど影響しない。一方、比較回数の削減、探索範囲の限定、配列演算への置換は、計算量または定数倍の処理時間を変え得る。

\subsection{オーダーとは何か}

ここでいう「オーダー」は、入力サイズ $N$ が大きくなったときの処理回数の増え方を表す。Big-O は漸近的な上界を表し、厳密な比例関係や実測時間そのものを表す記法ではない。最悪の場合、平均的な場合など、どの条件の計算量かも区別する。通常は Big-O 記法\index{big-o@Big-O 記法|textbf}で書き、定数倍や低次の項を落として、最終的に支配的になる項だけを見る。

\[
3N + 20 \rightarrow O(N), \qquad
5N \log N + 100N \rightarrow O(N \log N), \qquad
N^2 + N \rightarrow O(N^2)
\]

解析コードに現れる計算量の例を次に示す。

\begin{itemize}
\item $O(\log N)$: 範囲を半分ずつ絞る処理。二分探索など
\item $O(N)$: 1 回走査する処理。総和、平均、閾値判定、隣接差分など
\item $O(N \log N)$: ソートを含む処理。高速なソート、ソート後の探索など
\item $O(N^2)$: すべての組み合わせを調べる処理。全ペアの逐次比較など
\end{itemize}

たとえば $N = 10^6$ なら、$\log_2 N$ はおよそ 20、$N \log_2 N$ はおよそ $2 \times 10^7$、$N^2$ は $10^{12}$ である。この場合、\(N^2\) と \(N\log_2 N\) の間には約 5 万倍の差がある。小さなテストデータでは判別しにくい差も、入力が大きくなると処理時間を支配し得る。

ただし、オーダーが同じ実装どうしでも、1 要素あたりの演算数、メモリアクセス、関数呼び出しなどの違いによって処理時間は変わる。まず計算量を確認し、次に測定結果に基づいて定数倍の差を調べる。

$O(\log N)$ は問題サイズを反復ごとに一定比率で縮小する処理に現れ、$O(N \log N)$ は各要素に対する処理をその段数だけ行う場合に現れる。以下では、二分探索とマージソートを例として両者を説明する。

\subsubsection{二分探索ではなぜ \texorpdfstring{$O(\log N)$}{O(log N)} になるか}

\(\log N\) は、反復ごとに候補数を一定の比率で減らす処理に現れる。昇順に並んだ列から値を探す二分探索では、中央の値との比較によって、次に調べる範囲を左半分または右半分へ限定する。

\begin{lstlisting}[language=Python]
def binary_search(values, target):
    left = 0
    right = len(values) - 1

    while left <= right:
        mid = (left + right) // 2
        if values[mid] == target:
            return mid
        if values[mid] < target:
            left = mid + 1
        else:
            right = mid - 1
    return -1
\end{lstlisting}

要素数が \(N\) 個の場合、候補数は \(N \to N/2 \to N/4 \to \cdots \to 1\) と減少する。反復回数 \(k\) は \(N/2^k \leq 1\) を満たすため、\(k \geq \log_2 N\) である。したがって、二分探索の計算量は \(O(\log N)\) となる。

\subsubsection{ソートではなぜ \texorpdfstring{$O(N \log N)$}{O(N log N)} になるか}

挿入ソートやバブルソートの最悪計算量は $O(N^2)$ である。一方、マージソートやヒープソートの最悪計算量は $O(N \log N)$ である。Python の \code{sorted()} は Timsort を用い、最悪計算量は $O(N \log N)$、すでに整列した入力では $O(N)$ となる。

ここで \(N \log N\) と書くなら、その意味も説明する必要がある。典型例であるマージソートでは、まず列を半分に分け、さらにその半分へ分ける、という分割を繰り返す。この分割の深さは、およそ \(\log_2 N\) 段である。一方、各段では、分かれた小列どうしを併合する過程で、全体として各要素を 1 回ずつ見るので \(O(N)\) かかる。

\[
\text{各段の仕事量 } O(N)
\quad \times \quad
\text{段数 } O(\log N)
\quad = \quad
O(N \log N)
\]

ソートを前処理として行うと、後続の探索や近傍判定に必要な比較回数を減らせる場合がある。$O(N \log N)$ のソート後に線形走査を行う実装は、全ペアを比較する $O(N^2)$ の実装より、入力サイズの増加に対する演算回数を抑えられる。

データ数が 10 倍になったとき、$O(N^2)$ のソートの演算回数はおよそ 100 倍になる。一方、$O(N \log N)$ では、$N=10^6$ から $10^7$ へ増える場合の比は約 11.7 である。この増加率の差が、入力規模に応じてアルゴリズムを選ぶ根拠となる。

\subsection{オーダーが改善する例: 重複判定}

長さ $N$ の整数列について、同じ値が 2 回以上現れるかを判定する問題を考える。

最も素朴な方法は、すべての組 $(i, j)$ を比べることである。

\begin{lstlisting}[language=Python]
def has_duplicate_slow(values):
    for i in range(len(values)):
        for j in range(i + 1, len(values)):
            if values[i] == values[j]:
                return True
    return False
\end{lstlisting}

この方法では、最悪の場合ほぼすべてのペアを比べるので $O(N^2)$ になる。データ量が 10 倍になると、比較回数はおおよそ 100 倍に増える。

列をソートすると、同じ値は隣接して並ぶ。したがって、隣接要素の比較だけで重複を判定できる。

\begin{lstlisting}[language=Python]
def has_duplicate_fast(values):
    values_sorted = sorted(values)
    for i in range(len(values_sorted) - 1):
        if values_sorted[i] == values_sorted[i + 1]:
            return True
    return False
\end{lstlisting}

\code{sorted()} は最悪 $O(N \log N)$、その後の走査は $O(N)$ なので、全体の最悪計算量は $O(N \log N)$ である。全ペア比較を隣接要素の比較へ置き換えたことにより、計算量が $O(N^2)$ から $O(N \log N)$ へ変わる。

Python の \code{set(values)} を使えば、重複判定は平均的に $O(N)$ で実行できる。ここでは、ソート後の走査によって処理量を減らす考え方を説明するため、ソートを用いた例を示している。

未整列の列に対する線形探索は $O(N)$ であり、整列済みの列に対する二分探索は $O(\log N)$ である。探索が 1 回だけならソート時間が支配的になり得るが、同じ列を反復して探索する場合は、ソートと全探索を含む総演算回数を比較して前処理の採否を決められる。

\subsection{オーダーは同じで定数倍だけ改善する例}

今度は、$n \times n$ 行列 $A$ が対称行列かどうか、すなわち $A_{ij} = A_{ji}$ が成り立つかを調べる問題を考える。

ここでは入力が有限な実数だけを含む正方行列であるとする。NaN は自分自身とも等しくないため、対角成分を省略する前に除外する必要がある。最も素朴な方法は、すべての $(i, j)$ について比較することである。

\begin{lstlisting}[language=Python]
def is_symmetric_slow(A):
    n = len(A)
    for i in range(n):
        for j in range(n):
            if A[i][j] != A[j][i]:
                return False
    return True
\end{lstlisting}

これは $n^2$ 回程度の比較を行うので $O(n^2)$ である。

対称性の判定では、\(A_{ij}=A_{ji}\) と \(A_{ji}=A_{ij}\) が同じ比較に当たる。そこで、対角成分を除く上三角だけを調べれば、判定結果を変えずに重複を除ける。

\begin{lstlisting}[language=Python]
def is_symmetric_fast(A):
    n = len(A)
    for i in range(n):
        for j in range(i + 1, n):
            if A[i][j] != A[j][i]:
                return False
    return True
\end{lstlisting}

こちらも計算量のオーダーは $O(n^2)$ だが、比較回数は $n(n-1)/2$ 回であり、素朴な実装のおよそ半分である。入力サイズに対する増加率は変わらないものの、重複する比較を除いた分だけ実行時間の定数因子が小さくなる。

この変更では計算量のオーダーは変わらず、重複の除去によって定数因子だけが改善する。図~\ref{fig:vectorization-benchmark} の隣接差分フィルタも同じ分類に属する。比較回数の次数を下げたのではなく、Python が要素ごとに処理する回数を減らしたことが時間差の要因である。

\section{ベクトル化・型・逐次処理による改善}

\subsection{NumPy と pandas による高速化}

アルゴリズムを見直した後は、NumPy や pandas へ処理を移すことで、Python レベルのループを減らせる。特に差分計算、ソート、列抽出、フィルタは、これらのライブラリが得意とする。図~\ref{fig:vectorization-benchmark} からも、ベクトル化\index{べくとるか@ベクトル化|textbf}が速度に与える効果を視覚的に確認できる。

NumPy や pandas への置換だけでは、アルゴリズムの計算量は変わらない。全ペア比較などの不要な演算を削減した後、残った要素ごとの処理を配列演算へ置き換える。

\subsection{メモリとコピーの管理}
\index{めもりかんり@メモリ管理|textbf}
\index{びゅー@ビュー|textbf}
\index{こぴー@コピー}

大きな中間配列を反復して生成すると、メモリ使用量とデータ転送時間が増える。処理によっては、演算時間よりもメモリ確保と転送が総所要時間を支配する。

反復回数に加えて、配列のコピー回数とコピーした総バイト数も測定対象となる。必要な列と範囲だけを読み込み、中間配列の生成を減らせば、メモリ使用量と転送時間を抑えられる。

NumPy では、スライスが元配列とメモリを共有するビューになる一方、条件抽出は新しい配列を作る。次のコードで両者を確認できる。

\begin{lstlisting}[language=Python]
import numpy as np

values = np.arange(1_000_000, dtype=np.float64)
view = values[100:200]
copied = values[values % 2 == 0]

print(values.nbytes)
print(view.nbytes, np.shares_memory(values, view))
print(copied.nbytes, np.shares_memory(values, copied))
\end{lstlisting}

実行結果は次の通りである。

\begin{lstlisting}[numbers=none, xleftmargin=2\zw]
8000000
800 True
4000000 False
\end{lstlisting}

\code{nbytes} は配列要素が占めるバイト数を表す。\code{np.shares\_memory(a, b)} は 2 配列が同じメモリ領域を共有するかを調べる。この例では、\code{view} 自体が参照する要素は 800 バイト分だが、元配列のメモリを共有するため、\code{view} の要素を書き換えると対応する \code{values} の要素も変わる。\code{copied} は 50 万要素の独立した配列であり、新たに 4 MB を使う。なお、\code{nbytes} は Python オブジェクト自体の管理領域を含まないため、プロセス全体のメモリ使用量と完全には一致しない。

\subsection{ファイル分割、並列処理、逐次集計}
\index{ぶんかつよみこみ@分割読み込み|textbf}
\index{へいれつか@並列化|textbf}
\index{すとりーみんぐ@ストリーミング|textbf}

入力全体が利用可能なメモリを超える場合は、ファイルまたはチャンク単位で読み込み、次の処理に必要な情報だけを保持する。互いに独立した単位へ分割できる処理は、並列実行の候補となる。

逐次処理では、現在の計算に必要な状態だけを保持し、件数、合計、最小値などを入力ごとに更新する。保持する状態の大きさが入力件数に依存しなければ、集計用メモリを一定に保てる。

例えば、1 行に 1 個の測定値が書かれた \code{values.txt} の平均は、全行をリストへ保存せずに求められる。

\begin{lstlisting}[numbers=none, xleftmargin=2\zw, title={values.txt}]
1.5
2.0
4.0
2.5
\end{lstlisting}

\begin{lstlisting}[language=Python]
def streaming_mean(path):
    count = 0
    total = 0.0

    with open(path, "r", encoding="utf-8") as f:
        for line_number, line in enumerate(f, start=1):
            text = line.strip()
            if text == "":
                continue
            try:
                value = float(text)
            except ValueError as exc:
                raise ValueError(f"line {line_number}: {text!r}") from exc
            count += 1
            total += value

    if count == 0:
        raise ValueError("input contains no numeric values")
    return total / count


print(streaming_mean("values.txt"))
\end{lstlisting}

出力は \code{2.5} となる。引数 \code{path} は入力ファイルの場所であり、\code{enumerate(..., start=1)} はエラー箇所をファイルと同じ 1 始まりの行番号で報告するために使う。この関数が保持するのは現在行、件数、合計だけなので、入力行数が増えても集計用メモリはほぼ一定である。ただし、中央値や全体のソートのように全データの順序が必要な統計量は、この単純な方法だけでは正確に求められない。

\section{プロファイリングと低レベル実装}

\subsection{プロファイラによるボトルネックの特定}
\index{ぼとるねっく@ボトルネック|textbf}

関数ごとの呼び出し回数と所要時間は、プロファイラ\index{ぷろふぁいら@プロファイラ|textbf}で測定できる。例えば \code{cProfile}\index{cprofile@\code{cProfile}|textbf} は、関数自身の処理時間と、呼び出した関数を含む累積時間を出力する。

\begin{lstlisting}[language=Python]
import cProfile

cProfile.run("run_analysis()", sort="cumtime")
\end{lstlisting}

プロファイル結果では、呼び出し回数、1 回あたりの時間、累積時間を区別する。関数内部に入出力待ちが含まれる場合は、CPU 時間だけでなく経過時間も併せて測定する。

\begin{lstlisting}[numbers=none, xleftmargin=2\zw]
ncalls  tottime  cumtime  function
100000   1.25     1.40    check_pair
    10   0.02     2.10    read_all_files
\end{lstlisting}

この結果例では、\code{check\_pair} は 10 万回呼び出され、合計 1.25 秒を関数自身の処理に要している。\code{read\_all\_files} の累積時間 2.10 秒には、関数内から呼び出した処理も含まれる。改善候補は、各列の定義に基づいて選ぶ。

\subsection{C や C++ へ書き換えるという選択肢}

Python で作成した解析コードでも、計算量の多い部分だけを C や C++ で実装できる。移植する範囲は、アルゴリズムを整理し、プロファイルによって処理時間を支配する箇所を特定してから決める。

処理時間の主因がファイル入出力、不要なデータ変換、またはアルゴリズムにある場合、実装言語だけを変えても大きな改善は期待できない。低レベル言語への移行は、Python 側の測定によって計算コアを限定し、入出力を含む総所要時間に対する効果を見積もった後に検討する。

\begin{lstlisting}[language=C++]
for (std::size_t i = 0; i < n; ++i) {
    for (std::size_t j = i + 1; j < n; ++j) {
        if (std::abs(times[j] - times[i]) <= window) {
            ++count;
        }
    }
}
\end{lstlisting}

C++ への書き換えによって 1 回の比較に要する時間が減っても、上の二重ループの計算量は $O(N^2)$ のままである。アルゴリズム変更による演算回数の削減と、実装言語変更による 1 演算あたりの時間短縮を分けて測定する。

\subsection{Python からの C/C++ コード呼び出し}
\index{cython@Cython|textbf}
\index{pybind11@pybind11|textbf}

Python から低水準の実装を呼び出す方法には、\code{ctypes}、Python C API、pybind11、Cython がある。それぞれ、既存共有ライブラリの利用、C API による拡張、C++ インタフェースの公開、型付きコードのコンパイルという異なる用途を持つ。

\begin{lstlisting}[language=Python]
cdef int i
cdef double total = 0.0

for i in range(n):
    total += values[i]
\end{lstlisting}

この断片は Python の \code{.py} ファイルへそのまま書いて実行するコードではなく、Cython の \code{.pyx} ファイル内で、配列と長さを定義した関数に組み込んでコンパイルする例である。配列の要素アクセスも低水準化するには、配列側の型指定も必要になる。ここで \code{cdef} は Cython 特有の宣言であり、変数を Python オブジェクトではなく C の整数や浮動小数点数として扱わせるために使う。これにより、ループ内部の型判定やボックス化のコストを減らせる。

実装方法は、既存コードの言語、必要なインタフェース、測定された処理時間、保守とビルドの負担に基づいて選ぶ。

\begin{itemize}
\item \code{ctypes}: 既存の C 共有ライブラリを、追加の拡張モジュールをコンパイルせずに呼び出す。引数型と返り値型は Python 側で宣言する
\item Python C 拡張: Python の C API を直接使用する。参照カウントと例外処理を含め、C 側で Python オブジェクトを管理する
\item \code{pybind11}: C++ の関数やクラスに対する Python バインディングを C++ で記述する
\item Cython: Python に近い構文へ静的な型情報を追加し、C または C++ を経由して拡張モジュールを生成する
\end{itemize}

既存の C 共有ライブラリを呼ぶ場合は \code{ctypes}、C++ の関数やクラスを Python API として公開する場合は pybind11、Python に近いコードへ型を付けてコンパイルする場合は Cython が候補となる。言語境界のインタフェースを限定し、測定で特定した計算コアだけを分離する。pybind11 の最小構成は付録~\ref{app:pybind11} で説明する。

\begin{lstlisting}[language=Python]
result = fast_module.count_pairs(times, window)
\end{lstlisting}

Python 側の入出力契約をテストで固定すれば、同じ契約を保ったまま内部実装を置き換えられる。Cython や C++ へ移植しても計算量は自動では改善しないため、プロファイルによって処理時間を支配するループを特定し、アルゴリズムと実装言語の効果を分けて測定する。

\subsection{外部実装におけるアルゴリズムとデータ受渡しの確認}

外部の C や C++ 実装を参照する場合は、対象とする問題、採用したアルゴリズム、低レベル言語へ移した範囲、Python 側とのデータ受け渡しを確認する。

高速化の章では、このような例を参照しながら、次の二つを常に区別して考える。

\begin{itemize}
\item アルゴリズムを変えたから速くなったのか
\item 実装言語を変えたから速くなったのか
\end{itemize}

両者を同時に変更すると効果を分離できないため、同じ入力と出力条件の下で個別に比較する。

高速化のレポートでは、「NumPy にした」「C++ にした」という実装手段だけでなく、計算量、比較回数、メモリ配置、Python レベルのループ回数がどのように変化したかを説明する。

\section{高速化前後の比較と測定条件の報告}

高速化の結果は、変更前後の所要時間、比、測定条件を同じ表または出力欄へ記録する。次は報告形式を示すための仮想的な数値例である。

\begin{lstlisting}[numbers=none, xleftmargin=2\zw]
slow version : 182.4 s
vectorized   :  12.7 s
streaming    :   4.8 s
\end{lstlisting}

報告には、この形式で測定した値を記載し、続けて「比較回数を減らした」「Python ループを配列演算へ移した」「全件保持をやめた」など、変化を生じさせた実装上の差を示す。測定条件、測定値、変更内容を一組として記録する。

高速化の報告では、$O(N^2)$ から $O(N \log N)$ または $O(N)$ へ計算量を変えた改善と、同じオーダーのまま NumPy、Cython、C++ などで定数倍を変えた改善を区別する。前者はアルゴリズム、後者は実装効率の変更である。

\begin{lstlisting}[language=Python]
import numpy as np

values = np.array(data, dtype=np.float64)
diffs = np.diff(values)
count = np.count_nonzero(diffs > 0.25)
\end{lstlisting}

\section{章末課題：処理時間とメモリの測定}

\begin{enumerate}
\item \textbf{結果を保持したベクトル化}。
\verb|values = np.arange(1_000_000, dtype=np.float64)| について、各要素を二乗してから総和を求める処理を Python の \code{for} 文と NumPy の列演算で実装せよ。\code{np.isclose()} で結果が一致することを先に確認し、その後で \code{time.perf\_counter()} を使って各方法を 5 回ずつ測定せよ。最小値または中央値を報告し、1 回だけの値を比較しない理由を説明せよ。

\item \textbf{入力サイズと計算量の関係}。
本文の \code{has\_duplicate\_slow()} と \code{has\_duplicate\_fast()} を使い、\code{np.random.default\_rng(42).permutation(N).tolist()} で作った、重複がなく順序を乱した入力について \(N=1000, 2000, 4000\) の実行時間を測定せよ。整列済み入力では Timsort が線形時間で動くことがあり、最悪計算量の比較にはならない。\(N\) を 2 倍にしたときの時間比を求め、\(O(N^2)\) と \(O(N\log N)\) の予想と比較せよ。計算機や実行時の状態によって時間は変わるため、絶対時間ではなく比と傾向を説明せよ。

\item \textbf{ビューとコピーの影響}。
本文の \code{values}、\code{view}、\code{copied} を作り、\code{view[0] = -1} と \code{copied[0] = -2} を実行した後で \code{values[100]} と \code{values[0]} を表示せよ。前者だけが変化する理由を、\code{np.shares\_memory()} の結果と対応させて説明せよ。さらに \code{float32} と \code{float64} で同じ要素数の \code{nbytes} を比較せよ。

\item \textbf{逐次集計の検証}。
1 から 100000 までを 1 行ずつ書いたファイルを作り、本文の \code{streaming\_mean()} で平均を求めよ。期待値は \code{50000.5} である。同じファイルを全件リストへ読み込む実装も作り、結果の一致を確認せよ。両者が保持するデータ量を、入力行数 \(N\) に対するオーダーで説明せよ。

\item \textbf{プロファイル結果に基づく改善対象の選定}。
自分の解析スクリプト、または 1 問目の 2 実装を関数へ分けたスクリプトを \code{python -m cProfile -s cumtime script.py} で測定せよ。出力の \code{ncalls}、\code{tottime}、\code{cumtime} の意味を説明し、累積時間の上位 3 関数を記録せよ。そのうち改善対象に選ぶ関数と、選ばない関数の理由をそれぞれ述べよ。
\end{enumerate}

性能改善では、処理時間だけでなく計算結果の同一性も検証する。入力条件、実行環境、反復回数、代表値の選び方を記録しておけば、第三者も測定を再現できる。次章では、同時観測イベントの探索を題材として、データの読み込み、検証、可視化、フィット、性能測定を一つの解析へ統合する。
